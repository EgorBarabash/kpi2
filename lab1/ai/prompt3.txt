1. Критерій 2 ("усі PK - id") суперечив складеним PK у spec (Game_Account, Tournament_Application,
   Tournament_Application_Member, Player_Statistic). AI сам обрав критерій: додав усім id і від себе
   дописав "unique with ..." для пар, яких у spec немає.
2. Tournament_Application_Member - сполучна сутність без власних атрибутів (порушує критерій 1),
   tournament_id у ній дублюється через заявку (не 3NF), зв'язок Tournament - TAM зайвий.
   Причина - сам spec (зв'язки 4-5) вимагав цю сутність.
3. Кардинальності й типи, яких немає в spec:
   - Tournament_Application ||--o{ Encounter (plays_as_first/second) - команда обов'язкова,
     хоча в зустрічах наступних етапів учасники невідомі;
   - Encounter ||--|{ Match - щонайменше один матч, хоча запланована зустріч матчів не має;
   - stage int, description text - типи вигадані AI (у spec типів немає).
   Причина - spec не описував обов'язковість зв'язків і типи атрибутів.

Виправ ці розбіжності:
- прийняти єдиний PK id (uuid) для всіх сутностей, унікальність задати парами в spec;
- прибрати Tournament_Application_Member, зв'язок Tournament_Application - User зробити прямою N:M,
  правило "один гравець - одна заявка на турнір" записати як бізнес-правило;
- у розділі "Зв'язки" явно вказати обов'язковість (0..1 / 0..N);
- назви атрибутів статусу/ролі - status / role з типом enum;
- переписати критерії прийняття так, щоб вони покривали: Mermaid + рендер, PK, мітки зв'язків,
  заборону сполучних сутностей, 3NF, збіг назв spec = діаграма, дозволені типи, кардинальності.
