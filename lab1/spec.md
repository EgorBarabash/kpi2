# Специфікація ERD платформи аматорських кіберспортивних турнірів

## Намір

Побудувати концептуальну модель сутностей і зв'язків (ERD) для платформи аматорських кіберспортивних турнірів, щоб відобразити повний життєвий цикл турніру - від складу команди та подачі заявки до турнірної сітки, результатів матчів і статистики гравців - без деталей фізичної реалізації бази даних.

## Типи

- **team_status**: active, disbanded
- **team_member_status**: active, left, kicked
- **tournament_status**: registration, ongoing, finished
- **tournament_participant_status**: pending, accepted, rejected
- **encounter_status**: scheduled, ongoing, finished
- **team_role**: player, captain

## Сутності

**User (Користувач)** - зареєстрована особа: гравець або організатор.
Атрибути: id (PK), email (UK), hashed_password, nickname (UK), name, description, avatar_url, created_at.

**Game_Account (Ігровий акаунт)** - прив'язка користувача до його акаунта в конкретній грі.
Атрибути: id (PK), user_id (FK), game_id (FK), game_account_id.
Пара (game_id, game_account_id) унікальна.

**Game (Гра)** - гра, з якої проводяться турніри.
Атрибути: id (PK), name (UK), logo_url

**Team (Команда)** - група гравців, що виступає разом.
Атрибути: id (PK), name (UK), avatar_url, created_at, max_team_players, status (team_status).

**Team_Member (Учасник команди)** - членство користувача в команді з роллю та історією.
Атрибути: id (PK), team_id (FK), user_id (FK), joined_at, leave_at, status (team_member_status), role (team_role).

**Tournament (Турнір)** - змагання з однієї гри, яке створює організатор.
Атрибути: id (PK), organizer_id (FK), game_id (FK), name, created_at, start_at, prize_pool, currency, min_teams, max_teams, min_team_players, max_team_players, status (tournament_status).

**Tournament_Application (Заявка на турнір)** - заявка команди на участь у турнірі.
Атрибути: id (PK), tournament_id (FK), team_id (FK), status (tournament_participant_status).
Пара (tournament_id, team_id) унікальна.

**Encounter (Зустріч)** - протистояння двох заявок у турнірній сітці.
Атрибути: id (PK), tournament_id (FK), stage (назва етапу сітки), tournament_application_id_1 (FK), tournament_application_id_2 (FK), winner_tournament_application_id (FK), next_encounter_id (FK), status (encounter_status).

**Match (Матч)** - окрема гра (мапа) в межах зустрічі.
Атрибути: id (PK), encounter_id (FK), match_game_id, map_order, winner_tournament_application_id (FK).
Пара (encounter_id, map_order) унікальна.

**Player_Statistic (Статистика гравця)** - показники гравця в конкретному матчі.
Атрибути: id (PK), match_id (FK), user_id (FK), kills, deaths, assists.
Пара (match_id, user_id) унікальна.

## Зв'язки

1. **User - Team (N:M)**. Гравець може бути учасником багатьох команд, і команда може містити багатьох учасників. Зв'язок має власні атрибути, тому реалізований асоціативною сутністю Team_Member.
2. **User - Tournament (1:N)**. Користувач може створити багато турнірів, але турнір має лише одного організатора.
3. **Team - Tournament (N:M)**. Команда може подати заявку на багато турнірів, і турнір містить багато команд-учасників. Зв'язок має власні атрибути, тому реалізований асоціативною сутністю Tournament_Application.
4. **Tournament_Application - User (N:M)**. Заявка містить склад гравців (0..N), а користувач може бути заявлений у багатьох заявках. Власних атрибутів зв'язок не має, тому це пряма N:M без проміжної сутності. Бізнес-правило: у межах одного турніру користувач може бути заявлений не більше ніж в одній заявці.
5. **Tournament - Encounter (1:N)**. Турнір містить 0..N зустрічей, кожна зустріч належить строго одному турніру.
6. **Tournament_Application - Encounter (три зв'язки 1:N)**. Зустріч має першу команду, другу команду та переможця - кожна з них є заявкою і кожна необов'язкова (0..1): учасники зустрічей наступних етапів невідомі до завершення попередніх, переможець - до завершення зустрічі. Заявка може брати участь у 0..N зустрічах.
7. **Encounter - Encounter (1:N, рекурсивний)**. Зустріч має необов'язкове (0..1) посилання на наступну зустріч у сітці для просування переможця; до однієї зустрічі можуть вести 0..N попередніх.
8. **Encounter - Match (1:N)**. Зустріч складається з 0..N матчів (запланована зустріч ще не має матчів), кожен матч належить строго одній зустрічі. Переможець матчу - необов'язкова (0..1) заявка.
9. **Match - User (N:M)**. Кожен матч містить статистику для багатьох гравців, а гравець має статистику в багатьох матчах. Зв'язок має власні атрибути, тому реалізований асоціативною сутністю Player_Statistic.
10. **User - Game_Account (1:N)**. Користувач може мати 0..N ігрових акаунтів, кожен акаунт належить одному користувачу.

## Критерії прийняття

1. Модель описана в декларативному синтаксисі Mermaid (тип erDiagram); рендер (PNG) згенеровано з `.mmd`, зв'язки на ньому не накладаються.
2. Усі первинні ключі (PK) мають назву id та тип uuid. Природна унікальність задається в spec парами атрибутів і позначається на діаграмі.
3. Текст зв'язків у Mermaid - англійською, одним словом, без лапок.
4. N:M без власних атрибутів показується прямим зв'язком (`}o--o{`) без проміжної сутності; асоціативна сутність допускається лише тоді, коли зв'язок має власні атрибути.
5. Модель у 3NF: жоден атрибут не дублює дані, які можна отримати через інший зв'язок.Довідкові значення, що повторюються в кількох сутностях, виносяться в окрему сутність.
6. Назви й склад атрибутів на діаграмі збігаються зі spec; статуси й ролі мають назву status / role, а їхній тип - enum із розділу «Типи».
7. Типи атрибутів: ідентифікатори - uuid; текстові - string; кількості та порядкові номери - int; суми - decimal; дати - timestamp; статуси й ролі - enum-типи з розділу «Типи». Інші типи не використовуються.
8. Кардинальності й обов'язковість на діаграмі беруться з розділу «Зв'язки»; якщо обов'язковість у spec не вказана - це помилка spec, а не рішення для AI.
